# BREAK//174 Implementation Plan

> For agentic workers: use superpowers:executing-plans to implement this plan task by task.

**Goal:** Ship a usable first firmware implementation and the same C engine as a browser instrument.

**Architecture:** Integer-only C99 engine, one sample clock, deterministic phrase generation and bounded PCM memory. A thin adapter connects the pinned Dinghy platform. Native and WASM builds share the sound/gesture implementation.

**Tech Stack:** C99, Python 3 build/test utilities, WebAssembly, AudioWorklet, dependency-free HTML/CSS/JS.

**Spec:** ../specs/2026-10-16-break174-design.md

## Global Constraints

- Core rate 44100 Hz; PCM prints 22050 Hz, mono, one bar, two bounded banks.
- BPM 140–190; default 174; three style profiles; no original commercial recordings.
- No dynamic allocation, float, double, 64-bit division or hardware register access in core.
- Momentary actions never reset transport; release restores the running phrase position.
- Source and licensing accompany the platform; updater/rescue remain enabled.
- Initial release explicitly untested on physical FM-1; do not claim hardware qualification.
- This implementation covers a first alpha, not every future expansion in the design document.

## Review Focus

1. Simultaneously held effects and late note-offs must not leave effects stuck.
2. Host sample rate may be 48000; browser resamples the 44100 core rather than changing tempo.
3. Invalid persisted settings and command values must be bounded.
4. STOP and pending SAVE must not erase flash while tails remain audible.
5. PCM reverse/slice reads and long-run transport must remain within bounds.
